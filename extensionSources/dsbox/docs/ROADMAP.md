# DSBox — roadmap и чеклист

Документ составлен по состоянию исходников и локальной документации модулей на 22 октября 2026 года. Это план продукта, а не список подтверждённых дефектов: большая часть модулей уже реализована и имеет собственные тесты. Порядок отражает риски перед выпуском.

## Уже есть

- [x] Модульный C++20 framework: жизненный цикл модулей, зависимости, динамические плагины и типизированная шина сообщений.
- [x] Основа для standalone/headless-сценариев и абстракции оконного ввода.
- [x] INI и слоистая конфигурация; IPC с двумя форматами кадров.
- [x] Подпроцессы, планировщик, CLI и Android ADB.
- [x] Сетевой стек: URL/body, `file://`, HTTP/1.1, сокеты и раздельные TLS/trust-модули.
- [x] SDL backend, Vulkan renderer и retained UI с базовыми виджетами, вводом и инкрементальной раскладкой.
- [x] Launcher, ADB GUI tool и отдельный Windows mod-loader/runtime.
- [x] Unit-тесты для большинства библиотек; CI-конфигурация для Linux и Windows.

## P0 — подтвердить воспроизводимость сборки

- [ ] Прогнать чистую сборку и весь CTest-набор на Linux и Windows из актуального checkout; сохранить результаты pipeline.
- [ ] Подтвердить Windows CI на реальном runner: заметка в `.gitlab-ci.yml` прямо говорит, что job ещё не проверен end-to-end.
- [ ] Устранить расхождение между двумя preset-именами Windows: `x64-field` в `CMakePresets.json` и документированная проверка runner/toolchain.
- [ ] Проверить конфигурации с `DSBOX_WITH_OPENSSL=AUTO/ON/OFF` и `DSBOX_BUILD_TESTS=ON/OFF`, чтобы необязательный OpenSSL не ломал базовую сборку.
- [ ] Добавить короткие smoke-сценарии запуска для launcher и ADB tool на чистом build output, включая разрешение DLL/RPATH, config и shader paths.

**Готово, когда:** CI проходит на обеих заявленных платформах, а smoke-проверка подтверждает запуск без случайной зависимости от локальной среды разработчика.

## P1 — определить и собрать путь распространения

- [ ] Зафиксировать целевые артефакты: framework SDK, launcher, ADB tool и/или mod-loader bundle; определить поддерживаемые ОС и архитектуры.
- [ ] Добавить CMake install/package правила для библиотек, заголовков, runtime-зависимостей, конфигов, шейдеров и примеров модулей. Сейчас в корневой сборке не обнаружены `install()`/CPack правила.
- [ ] Описать структуру установленного пакета и команды сборки/запуска в README; `docs/BUILD_LAYOUT.md` сейчас описывает прежде всего внутреннюю раскладку build output.
- [ ] Добавить версионирование/совместимость ABI и правила для плагинов: что проверяет `VersionRequirement`, что обещает проект между релизами.
- [ ] Подготовить release checklist: архивы, символы отладки, лицензии сторонних зависимостей, контрольная сумма и заметки о выпуске.

**Готово, когда:** чистый пакет можно установить/распаковать на поддерживаемой ОС и запустить по опубликованной инструкции.

## P1 — закрыть пользовательский сценарий моддинга

- [ ] Проверить end-to-end сценарий на отдельной тестовой программе: loader запускает процесс, runtime поднимает Context и загружает включённый мод из `modules.ini`.
- [ ] Добавить тестируемые проверки конфигурации/логирования и сценария отказа загрузки мода; для runtime пока отмечено отсутствие собственных автоматических тестов.
- [ ] Документировать установку, структуру `dsbox/`, формат `modules.ini`, логи, выключение/удаление и совместимость с целевой игрой.
- [ ] Явно определить политику anti-cheat compatibility: текущая реализация проверяет ограниченный список имён процессов; расширять его только по подтверждённой необходимости и документированным именам.
- [ ] Решить, нужен ли проекту host API для модов сверх `IModule`/`Context`; `dsbox_mod_runtime/Agent.md` оставляет это до появления конкретного мода.

**Готово, когда:** есть воспроизводимый тестовый host и инструкция, по которой пользователь может включить мод и понять причины отказа.

## P2 — зафиксировать открытые продуктовые решения

- [ ] Выбрать политику Windows системных CA: `dsbox_net_tls_systemca` читает Current User, но не Local Machine. До решения оставить поведение fail-closed и явно описывать область доверия.
- [ ] Определить желаемую поддержку macOS. Текущие presets/CI заявляют Linux и Windows; наличие POSIX-кода само по себе не подтверждает поддержку macOS.
- [ ] Для UI определить критерии готовности v1 и проверить оставшиеся ограничения измерения текста/layout, ввод с клавиатуры и доступность. `dsbox_ui/Agent.md` описывает сознательные границы текущей реализации, а не обязательные дефекты.
- [ ] Решить, нужен ли `file://` только для чтения; запись в локальные файлы явно исключена из текущего объёма.

## Рекомендуемый порядок

1. P0: чистая сборка, Windows CI и smoke-запуски.
2. P1: определить поддерживаемые продукты/платформы и сделать install/package.
3. P1: проверить и документировать пользовательский сценарий моддинга.
4. P2: принять решения по CA, macOS и критериям UI v1.

## Как поддерживать чеклист

- Отмечать пункты только после проверки на чистом окружении или после зафиксированного решения владельца проекта.
- Для найденного бага добавлять регрессионный тест в тесты соответствующего модуля.
- При изменении публичного API обновлять README и документацию модуля вместе с кодом.
